## └─[[solana.com/docs/core/accounts](https://solana.com/docs/core/accounts)]

>An **account** is Solana's fundamental data unit for storing state. The network stores all state in a key-value store where each key is a 32-byte (256-bit) address and each value is an account.

## Key facts

>- **Structure**: <u>Every account has the same five fields</u>: **lamports**, **data**, **owner**, **executable**, **rent_epoch**.

>    <div>
>    - `lamports`: The balance of SOL held by the account. A lamport is the smallest fractional unit of SOL.
>      - $1\text{ lamport} = 0.00\text{\_}000\text{\_}000\text{\_}1\text{ SOL} = 1 \cdot 10^{- 9}\text{ SOL.}$
>      - $1\text{ SOL} = 1\text{\_}000\text{\_}000\text{\_}000\text{ lamports} = 1 \cdot 10^{9}\text{ lamports.}$
>    - <div className="reset-theme">`data`: **Account state** or **program bytecode**. Max 10 MiB. Owner-writable only.</div>
>      - <b>System Accounts (Standard Wallets)</b>: <u>The `data` field is completely empty (0 bytes).</u> Your native SOL balance is tracked in the account's metadata header, not inside this data buffer.
>      - <b>Data Accounts (PDAs & Token Accounts)</b>: <u>The field holds passive state</u>. For example, a Token Account's `data` field stores a serialized struct containing the token mint, your wallet address, and your current token balance.
>        <div className="relative pl-8">
>          <div style={{ marginBottom: "4px" }}>
>            &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;↓
>          </div>
>          <Accordion title="Program-Derived Data Accounts">
>          <u>In short, it either holds passive data or active code.</u> If you think about it carefully, this leads to a fundamental architectural conclusion: <u>since the `data` field can hold either account state or program bytecode, a deployed smart contract is entirely stateless. The executable bytecode is stored in one account (the <b>Program Account</b>), and the contract must necessarily store its data in entirely separate accounts (<b>Data Accounts</b>).</u>
>          
>          ### How a Data Account is Associated with a Program
>
>          Because a smart contract (Program Account) is completely stateless, it needs a secure, verifiable way to connect to the separate Data Accounts that hold its state. This association is built on two pillars: Program Derived Addresses (PDAs) and Ownership.
>          
>          1. <b>The Cryptographic Link (Deriving the Address)</b>: When a program needs to create a new Data Account (for example, to store a new player's stats), it does not generate a random private key. Instead, it derives a PDA by hashing specific "seeds" together with its own Program ID.
>
>             For example, a game contract might derive a Data Account address using the seeds: `["player_stats", Player_Wallet_Pubkey] + Program_ID`. Because the Program ID is mathematically baked into the address generation, this creates a deterministic, unbreakable link between the program and the data account. The program will always know exactly where to find the user's data just by re-hashing those seeds.
>          
>          2. <b>The Security Link (Assigning Ownership)</b>: Deriving the address is only half the process. When the program actually sends the Cross-Program Invocation (CPI) to the System Program to allocate memory for this new Data Account, it explicitly sets the owner field of that new account to its own Program ID.
>             
>             This locks the association at the runtime level. Once the Data Account is created with the program assigned as the owner, the Solana operating system enforces the rule that only that specific program can ever write to or modify the data field of that account.
>          
>          3. <b>The Execution Flow</b>: When a user wants to interact with the contract (e.g., 'Level up my character'):
>             1. The user sends a transaction to the Program Account.
>             2. The user includes the derived Data Account in the transaction instructions.
>             3. The program verifies that the provided Data Account address matches the expected PDA derivation (confirming it is the correct account).
>             4. Because the program is the official owner of that Data Account, the runtime grants the program write-access to update the level in the Data Account's data buffer.
>          </Accordion>
>          <div style={{ lineHeight: "1", marginBottom: "2px" }}>
>            &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;↑
>          </div>
>        </div>
>      - <b>Program Accounts (Smart Contracts)</b>: <u>The field holds active executable bytecode. When you deploy a program, the compiled sBPF binary (the _.so_ file) is stored directly inside this data buffer so the network can execute it.</u><br />
>        <div style={{ marginBottom: "4px" }}>
>          &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;↓
>        </div>
>        <Accordion>
>
>        A program account uses the exact same underlying Rust struct as any standard Solana account (`Account` or `AccountInfo`). It has five fields:
>
>        ```rust Solana Account
>        pub struct Account {
>            pub lamports: u64,
>            pub data: Vec<u8>,
>            pub owner: Pubkey,
>            pub executable: bool,
>            pub rent_epoch: Epoch,
>        }
>        ```
>
>        Because virtually <u>all modern Solana smart contracts are deployed using the <b>BPF Upgradeable Loader</b></u> (`BPFLoaderUpgradeab1e11111111111111111111111`), <u>a deployed program is actually split across two distinct accounts: the <b>Program Account</b> and the <b>ProgramData Account</b></u>.
>
>        1. **The Program Account (The Program ID)**: <u>This account's public key is the Program ID that users and dApps interact with. It contains no executable bytecode; instead, it acts as a lightweight pointer to the account that does.</u>
>
>           | Limit | Value | Source |
>           | :--- | :--- | :--- |
>           | `lamports` | `~0.00114 SOL` (890,880 lamports) | Funded during deployment to cover the rent-exempt minimum for exactly 36 bytes. |
>           | `owner` | `BPFLoaderUpgradeab1e...` | <u>The System Program assigns ownership to the BPF Upgradeable Loader during deployment.</u> |
>           | `executable` | `true` | Flipped from `false` to `true` by the BPF Loader during the final deploy transaction. |
>           | `rent_epoch` | `0` or `u64::MAX` | Set by the runtime to indicate rent-exempt status. |
>           | `data` | 36 bytes | Serialized enum: `UpgradeableLoaderState::Program`. |
>
>        2.
>        </Accordion>
>      - <b>Max 10 MiB</b>: This is the absolute maximum storage limit a single account can hold. You cannot upload a 1 GB database into one Solana account; if you need more space, you must span the data across multiple accounts.
>    - `owner`: The <b>public key</b> of the program authorized to mutate this account.
>    - `executable`: A boolean flag (`true` or `false`).
>    - `rent_epoch`: Epoch metadata for storage tracking.

> - **Address**: Each account is identified by a unique 32-byte address (either an **Ed25519** public key or a PDA), <u>displayed as a **Base58**-encoded string</u>.
>
> <div className="colored-block relative pl-8 text-[#3C5FD3] dark:text-[#07A6AE]">
>   <span className="absolute left-0 top-0">↳</span>
>   <div>
>     <Accordion title="How Base58 Works">
>     
>     Base58 is a data encoding scheme originally created by Satoshi Nakamoto for Bitcoin. It starts with the standard 62-character alphanumeric alphabet (A-Z, a-z, 0-9) and <u>strips out four specific characters that cause visual confusion</u> in many fonts:
>     
>     - `0`—the number 'zero'.
>     - `O`—the capital letter 'o'.
>     - `l`—the lowercase letter 'L'.
>     - `I`—the capital letter 'i'.
>
>     It also excludes special symbols like `+` and `/` (which are used in Base64). This ensures that when you double-click an address, your computer highlights the entire string seamlessly without breaking on punctuation.
>
>     Under the hood, <u>to generate the string you see on your screen, the system takes the 32 raw bytes of your Solana public key, treats it as one massive integer, and continuously divides it by 58. It then uses the remainders to select characters from the 58-character alphabet.</u>
>     
>     **Why Solana Uses Base58**
>     
>     - **Error and Phishing Prevention**: By removing ambiguous characters, Base58 makes it nearly impossible for users to make a typo or fall for scams where an attacker generates an address that looks visually identical to your real one. If you see a round circle character in a Solana address, it is guaranteed to be a lowercase 'o', because the capital 'O' and zero '0' do not exist in the system.  
>     - **Data Compression (Shorter Strings)**: Base58 has 58 possible values per character position, whereas Base16 only has 16. <u>This means Base58 can pack more data into a shorter space.</u> A Solana public key is 32 bytes of raw data. If Solana used Base16 like Ethereum, every address would be 64 characters long. <u>By using Base58, Solana compresses those 32 bytes down to just 43 or 44 characters, making addresses more manageable for mobile screens.</u>

>     - **Program Derived Address (PDA)**: Deterministically derived from a **Program ID** and seeds (<u>no private key</u>).
>
>- **Ownership**: Only the account's owner program can modify its data or debit lamports. Any program can credit lamports to any writable account.
>  <div className="colored-block relative pl-8 text-[#3C5FD3] dark:text-[#07A6AE]">
>    <span className="absolute left-0 top-0">↳</span>
>    <div>
>    1. Every account on Solana is assigned an 'owner' (<u>a specific program</u>—on Solana, the terms 'program' and 'smart contract' are completely synonymous and used interchangeably). This rule dictates that only this owning program has the authority to alter the data stored inside the account or withdraw money (debit lamports).
>    2. While withdrawing funds is strictly locked down, depositing funds is open. Any program or user can send money (credit lamports) to your account, provided the transaction flags the account as 'writable' (capable of receiving balance changes).
>
>    At first glance, '1.' appears to be a chicken-and-egg paradox: if every account requires a program to own it, and every program is itself an account, how can anything exist in the first place?
>
>    1. The statement '<b>every program is itself an account</b>' is literal: <u>programs do not exist as distinct entities outside the account model</u>. Unlike architectures such as Ethereum—where smart contracts are specialized runtime objects with their own internal storage trie—<u>Solana treats programs as <b>stateless data accounts</b> containing compiled <b>bytecode</b></u>.
>    2. An account becomes a program through the combination of two specific fields:
>
>       1. <b>The `executable` flag is set to `true`</b>.<br />
>          <Info>
>          When a transaction invokes an instruction targeted at a public key, the Solana runtime inspects this flag. If `executable == false`, the runtime rejects the execution attempt immediately. If `executable == true`, the runtime confirms: 'This public key represents genuine, verified program bytecode'. <u>It proceeds to load the code and delegates execution to an on-chain interpreter or JIT compiler, passing the account's raw byte payload (`account.data`) to the Solana Virtual Machine (<b>SVM</b>):</u>
>          - <b>SBF Bytecode</b>: <u>The bytes in `data` are compiled machine code based on extended Berkeley Packet Filter (eBPF/**SBF**)</u>.
>          - <b>Just-In-Time (JIT) Compilation</b>: Rather than slowly interpreting instructions one by one, high-performance <u>Solana validators compile that SBF bytecode directly into native x86-64 machine instructions on the fly</u> (or cache the compiled version).
>          - <b>Execution</b>: <u>The runtime jumps directly to the entry point function within that compiled binary, passing in the remaining accounts and parameters provided by the transaction</u>.
>          </Info>
>       2. <b>The owner is set to an on-chain Loader</b>: <u>A program account is owned not by standard users, but by a native runtime loader</u> (such as the BPF Upgradeable Loader).
>
>    Solana breaks this loop through native runtime programs, which are hardcoded directly into the validator core software at genesis rather than deployed as regular accounts:
>
>    The System Program: Standard user wallets (keypairs) and newly initialized accounts are owned by the native System Program (address 11111111111111111111111111111111). When a standard wallet is created or funded, the System Program acts as its default owner.
>
>    Loader Programs: Smart contracts on Solana are simply data accounts marked as executable and owned by a native runtime loader (such as the BPF Upgradeable Loader). Because these loaders are baked directly into the Solana client architecture, they serve as the root authority for executable code without needing another contract above them.
>
>    Transfer of Ownership: To create a custom state account for your dapp, the System Program allocates the space and then transfers the ownership of that account to your custom deployed program's public key. From that moment on, only your program has the cryptographic authority to mutate that data or drain its balance.
>
>    While debiting funds and mutating state are strictly restricted to the owning program, depositing funds is open to everyone: any user or external contract can credit lamports to any account, provided the account is marked as writable in the transaction.
>    </div>
>  </div>
>- **Account storage**: Every account must hold a refundable minimum lamport balance proportional to its data size to remain onchain.
>  <div className="relative pl-8 text-[#3C5FD3] dark:text-[#07A6AE]">
>    <span className="absolute left-0 top-0">↳</span>
>    <div>
>    - <b>The Zero-Cost State Attack Vector</b>: If creating persistent on-chain state only incurred a one-time transaction fee (a fraction of a cent), an attacker with a few hundred dollars could issue millions of instructions allocating maximum-size accounts. Because blockchain storage is permanent by default, those bytes cannot be garbage-collected without a protocol-level rule. The attacker would pay once, but every validator on the network would be forced to carry that payload indefinitely.
>    - <b>RAM Saturation and Out-Of-Memory (OOM) Crashes</b>: Solana is engineered around sub-second finality and around 200ms slot times. To achieve parallel transaction execution via the Sealevel runtime, the validator engine cannot afford slow random disk lookups:
>
>      - <b>AccountsDB Architecture</b>: Solana validators maintain account indices, public key lookups, and active account structures directly in high-speed RAM and memory-mapped files (mmap).
>      - <b>The Memory Cliff</b>: If an attacker floods the state, the memory footprint of AccountsDB surges past physical RAM limits (typically 256 GB–512 GB on validator machines).
>      - <b>OOM Killer</b>: When the operating system runs out of physical memory, the Linux kernel's Out-Of-Memory (OOM) Killer intervenes and forcibly terminates the solana-validator process.
